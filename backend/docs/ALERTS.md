# Alerts: what tells you something is wrong

Seven alerts. Each has one place it is set up, one receiver and one thing to do. **Receiver for all seven: the founder** (`[Founder email]`, plus the phone app of the tool where one exists). There is no second person, so each alert must be quiet enough that it never gets ignored: the numbers below are starting values to tune after the first real week, not measured limits.

Set-up steps with a way to check each are in `FOUNDER_CHECKLIST_PROD.md` (steps 3, 4 and 5). Nothing below works until its step is done; today (2026-10-29) **none of the seven exists** (KNOWN_GAPS F2-01, F2-02, L4-05, X-06).

| # | Alert | Fires when | Set up in | What the founder does |
|---|---|---|---|---|
| 1 | **New Sentry issue in production** | An error with a new fingerprint appears with `environment = production`. | Sentry: Alerts, Issue alert, condition "A new issue is created", filter environment `production`, action: email the founder. | Open the issue, read the route and release (commit). If it is on a payment or sign-in route treat it as urgent; otherwise note it and fix in the next phase. If a new deploy caused it, roll back (`RELEASE.md` section 4). |
| 2 | **Error-rate spike** | Many errors in a short time, even if each is an old issue. Starting value: more than 10 error events in 5 minutes, production. | Sentry: Alerts, Metric alert on error count, environment `production`, same email. | Look at Render logs for the minute it started (`"level":"error"`, the `route` and `release` fields). A spike right after a deploy means roll back; otherwise check `/readyz` (database) and the Razorpay and email provider status pages. |
| 3 | **Payment flagged** | A payment was captured by Razorpay but cannot be honoured, or a refund's outcome is unknown. Raised by the code, once per case, with the fixed text "Payment flagged for manual review" and tags `alert=payment_flagged`, `kind=needs_review` or `refund_outcome_unknown` (no ids, no personal data). | Sentry: Alerts, Issue alert, "Every time an event is seen" with filter tag `alert` equals `payment_flagged`, environment `production`, email **and** phone push. | Open `/admin/`, Payments, filter "needs review", read the note, **refund in the Razorpay dashboard** (the system never refunds by itself), tell the student. The flag stays on as the record. Same day. |
| 4 | **Webhook failures** | Razorpay's push to `/api/v1/payments/webhook/` is failing, so paid students stay at "Still Waiting" (F6-07). | Two places: (a) Sentry issue alert with filter "transaction contains `payments/webhook`", every time, production; (b) Razorpay dashboard, Webhooks, delivery log (check after every deploy and weekly; whether Razorpay also emails on repeated failures is unconfirmed, so do not rely on it). | A 5xx on the webhook is a bug: read the Sentry issue. Many "invalid signature" lines instead mean `RAZORPAY_WEBHOOK_SECRET` on Render does not match the secret in Razorpay. Razorpay retries, so fix quickly; nothing is lost while it keeps retrying. |
| 5 | **Cron heartbeat missed** | The clean-up job did not report success within its grace time, or reported failure. Every 5 minutes expected; alert after 15 minutes of silence. | The heartbeat monitor (a service such as Healthchecks.io or Better Stack; both advertise a free tier, confirm current limits): one check, period 5 minutes, grace 10 minutes, email the founder. The job reports through `manage.py ping_heartbeat` (`HEARTBEAT_URL`; `/fail` is called when the job fails). | Open the cron job's latest run in Render (Logs). A failed step prints which one. Nothing breaks within hours (a lapsed bed hold also expires when it is read), but old OTP codes and event ids pile up and, later, reminders stop. Re-run it from Render ("Trigger run") once the cause is fixed. |
| 6 | **Uptime down** | `/healthz` or `/readyz` on production stops answering 200. | Uptime monitor (same kind of service): two checks on the **production** host only. `/healthz` every minute; `/readyz` every 5 minutes (it touches the database). Alert after 2 failures in a row, email and phone push. **Never monitor staging** (it must sleep; a monitor would keep it awake and use up its free hours). | `/healthz` down: the service is down or deploying; check Render Events, roll back if it is a bad deploy. `/healthz` fine but `/readyz` 503: database problem; check Supabase (paused, connections, status page). |
| 7 | **Backup workflow failed** | The daily encrypted backup run is red, including "no backup was made because the secrets are missing" (the workflow now fails on purpose until `BACKUP_DATABASE_URL` and `BACKUP_AGE_PUBLIC_KEY` exist). | GitHub: Settings, Notifications, Actions: "Send notifications for failed workflows only". GitHub emails the person who last edited the workflow's schedule. Back-stop: every Monday run `gh run list --workflow backup.yml --limit 3` or open the Actions tab and confirm a green run from the last 2 days with an artifact. | Open the failed run's log. Most likely: the database URL changed or the project is paused (Supabase), or the secrets were removed. Run it again by hand ("Run workflow"). A backup you have not seen succeed does not exist. |

## Things to know

- **Silence is not good news.** Alert 5 and the Monday backup check exist because a job that stops running sends no error. GitHub's documentation says scheduled workflows in a public repository are switched off after 60 days without repository activity (recalled from GitHub's docs, confirm); the Monday check catches that.
- **Sentry has a free quota.** Alert 2's threshold protects it too: a spike that repeats can use the month's events in hours. `SENTRY_TRACES_SAMPLE_RATE` stays low (checklist step 3).
- **Privacy.** Alert text and tags carry no emails, phone numbers, names or ids. Look the case up in `/admin/` instead of putting identifiers into a tool that is not ours.
- **The payment alert is raised by a logging handler** (`PaymentFlagHandler`, `apps/core/sentry_config.py`) that recognises the two ERROR lines the payment code already writes. Payment code itself was not changed. If either log message is reworded, `apps/core/test_phase2.py` fails.
- **Drill each alert once** after it is created (checklist steps 3 to 5 say how), otherwise you only find out it is broken when you need it.
